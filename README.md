## 产品与使用流程

问题假设是：现场参与者不容易知道旁边的人在做什么，也缺少自然开口和寻找帮助的入口。目前没有已完成用户访谈或真实活动效果数据，不把产品假设写成实测结论。

1. 在首页查看作品、现场信息，翻开或重抽破冰任务。
2. 进入 `/join`，选择已有队伍，或公开登记队伍名称、作品名称和简介。页面说明三项内容会显示在大厅、投票页和大屏，并提示不要填写私人联系方式。
3. 完成面对面破冰后主动确认；发布求助，由另一位参与者认领，再由发起者或认领者标记解决。也可为队伍喝彩、分享项目里程碑。
4. 在 `/vote` 了解作品并投出人气票，以服务器成功响应为准。本机演示模式与正式票库分离。
5. `/screen` 每 3 秒读取快照，显示现场互动、求助、真实票数与加入二维码。
6. `/play` 提供 30 秒声浪接力，默认使用按钮，麦克风是可选的本机音量反馈。

自助登记成功后会选中创建的队伍，并提供“查看我的作品”链接。名单从服务器状态更新，首页、投票页和大屏使用独立的作品名称；旧队伍没有作品名时仍显示原队伍名称。新队伍初始为零票，登记本身不会生成投票。

## 页面与数据边界

| 路径 | v14 已实现的功能 |
| --- | --- |
| `/` | 活动信息、翻卡与重抽、项目详情、现场互动入口 |
| `/join` | 队伍与作品自助登记、选择队伍、破冰确认、喝彩、求助发布和认领及解决、进展播报 |
| `/vote` | 作品详情、正式投票、真实票数和占比横条、同票并列、本机演示、花束庆祝 |
| `/screen` | 现场动态、求助状态、真实票数及占比、加入二维码、用户主动全屏 |
| `/play` | 30 秒声浪接力、按钮参与、可选本机音量反馈、结束后主动分享破冰事件 |
| `/admin` | 口令控制的隐藏事件、解决求助、清除种子演示事件 |

人气榜使用服务端全量有效票数，零票队伍不授予名次，同票并列。声浪只作本机娱乐测量，未经分贝校准；评委榜待录入，总榜规则待配置。页面没有已确认的评委身份、评分维度、评分权重或官方综合分。当前庆祝使用花束，不包含火箭庆祝。

## 自助登记与防重复

队伍名称为 2-28 个字符、作品名称为 2-40 个字符、简介为 4-90 个字符；前后端均校验必填、长度和不可显示的控制字符。名称比较会处理 Unicode 兼容形式、连续空白和 ASCII 字母大小写，已存在的队伍名或作品名会被拒绝。历史队伍没有独立作品名时，以队伍名参与作品名称判重。

登记会真实写入 D1。前端在提交期间锁定，服务器以匿名标识和请求 ID 派生稳定记录 ID，并执行条件写入。同一次请求并发发送或写入成功后丢失响应，再以同一请求 ID 重试，返回原记录，不再创建一条；同一请求 ID 不能悄悄换成不同内容。

失败时当前页面保留输入。服务器已确认成功但列表刷新失败时，提示稍后自动同步，不要求再次登记。请求 ID 保存在当前页面内存；这不是跨刷新、跨设备的持久离线队列。登记没有实名审核、所有权验证、自助编辑或撤销机制，也不能据此承诺防止恶意批量注册。

## API 与持久化

技术栈：React 19、TypeScript、Vinext、Cloudflare Workers、D1、Drizzle。

| API | 行为 |
| --- | --- |
| `GET /api/state` | 返回 `teams`、最近最多 150 条 `events`、`serverNow`、全量 `voteCounts` 和 `totalVotes`；队伍含 `projectName` |
| `POST /api/action` | 接受 `kind` 和匿名 `actor`；支持登记、喝彩、破冰、求助、进展、投票、认领和解决 |
| `POST /api/admin` | 验证独立管理口令后执行隐藏事件、解决求助或清除演示事件；生产无口令时拒绝管理操作 |

登记请求的 `kind` 为 `team`，字段为 `name`、`projectName`、`idea` 和 UUID 格式 `requestId`；成功返回 `teamId`。其余互动需要有效队伍 ID。事件快照不公开 `actor`，认领事件的内部关联备注不返回给客户端。用户提交的展示文字按纯文本渲染。

首次读取空数据库时会建立四支示例队伍和三条标记为演示的事件。示例队伍有标识；服务器接受的正式事件不等于通过身份认证的参赛记录。正式票只统计 `kind=vote`、`status=open`、`demo=0` 的记录。演示票只在本机 React 状态中变化，刷新后消失。

正式投票用单条条件 SQL 写入，服务端按匿名标识限制当前数据库内总共一张正式票。隐藏既有票不会恢复额度。系统尚无活动 ID 或多场活动隔离，同一库复用于下一场活动需要另行设计。

## 本地运行与数据库迁移

要求 Node.js 22.13+ 和 npm。下列命令用于新的本地数据库，在仓库根目录执行；先核对数据库是否已有迁移，不要重复执行同一 SQL 文件。

```sh
npm ci
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_massive_hellfire_club.sql
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0001_hot_harpoon.sql
npm run dev
```

已有上一版结构的本地库只需第二个迁移。`0001_hot_harpoon.sql` 的唯一结构变更是给 `teams` 增加 `project_name TEXT NOT NULL DEFAULT ''`；不删除队伍或票数，旧版写入可继续使用默认空值。命令以当前进程输出的端口为准；构建后也可用 `npm start` 运行本地 Worker 预览。

生产发布必须先核对真实 D1 绑定 `DB`、迁移状态、备份及独立 `ADMIN_PIN`。本地初始化示例不是生产发布命令。本项目通过原 Sites 发布流程部署；独立部署须使用自己的托管配置、数据库与口令。仓库配置元数据不能替代身份验证凭据，不提交真实口令、访问令牌或私有环境文件。
